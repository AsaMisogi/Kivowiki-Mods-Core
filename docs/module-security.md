# 模块安全与分发规范

本文定义 Kivowiki-Mods 清单 v4 的模块、依赖、权限、签名、来源、审核和安装策略。管理器允许用户自主安装无签名、未认证或带风险提示的包；提示用于帮助判断，不代表担保，也不会故意制造反复确认。

## 责任边界

- 第三方模块由模块作者提供，其安全性、真实性、质量、维护状态和服务可用性不由 Kivowiki-Mods 保证。
- 用户确认安装即表示接受所选权限和第三方代码风险。管理器负责展示信息、执行已实现的权限边界、隔离故障和保存本地状态。
- 自动扫描只能发现明显代码特征，既可能漏报，也可能误报。无提示不等于安全，有提示也不等于恶意。
- 页面模式为了实现深度页面增强，运行在 KivoWiki 页面环境，不能获得严格沙箱同等级别的隔离。低信任模块应使用 `sandbox` 或全局安全模式。
- 依赖是可复用能力包，不是权限提升通道。依赖没有独立权限开关：页面模式下与调用模块处于同一页面环境，因此仍需审阅和信任；严格沙箱中则不能访问 KivoWiki 页面、扩展 API 或网络。

## 清单类型与名称

- `type: module` 表示包含用户功能与页面逻辑的模块；模块可以声明设置、权限和依赖。
- `type: dependency` 表示只提供能力的依赖包；入口必须是返回 `{ create(dependencies) {} }` 的表达式，不得自行挂载业务 UI。
- 所有清单 `name` 必须以 `Kivowiki-Mods-` 开头，例如 `Kivowiki-Mods-reading-progress`。内部 `id` 继续使用简短的小写标识，用于存储和关系解析。
- 模块 ID 与依赖 ID 共享同一命名空间，不能跨类型重名。

## 权限声明

`permissions` 是对象数组。`reason` 应使用普通用户能理解的一句话说明用途；`optional: true` 表示用户可在安装时取消。未知权限允许出现在清单中并允许安装，但当前管理器不会开放对应能力。

| 权限 | 能力 | 模式 |
| --- | --- | --- |
| `page.read` | 读取当前页面 DOM、文字和路由 | page |
| `page.modify` | 修改当前页面 DOM、样式和交互 | page |
| `storage` | 使用模块 ID 隔离的本地业务存储 | page |
| `network.read` | 使用只读 GET/HEAD 数据能力 | page |
| `assets` | 读取模块包内资源 | page / sandbox |
| `settings` | 读取和保存模块设置 | page / sandbox |
| `ui` | 使用严格沙箱受限 UI 协议 | sandbox |

权限声明不会扩大浏览器扩展自身权限。页面代码仍可能直接使用网页环境已有能力，因此 `page` 模式的权限是一份安装提示和宿主 API 边界，不是浏览器进程级安全沙箱。

## 数字签名

当前支持 `ECDSA-P256-SHA256`。发布者在 `publisher.publicKey` 放入 P-256 JWK 公钥，在 `signature.value` 放入 Base64 签名。私钥必须离线保管，不能写入源码、模块包、管理器或社区仓库。

签名载荷按以下规则生成：

1. 从原始 `module.json`、`dependency.json` 或 `manifest.json` 删除顶层 `signature`。
2. 除清单文件外，对包内每个文件计算 SHA-256，小写十六进制表示，以规范化相对路径为键。
3. 构造 `{ "manifest": unsignedManifest, "files": fileHashes }`。
4. 对象键按 Unicode 字符串升序递归排列；数组保持原顺序；不添加空格或换行，生成规范化 JSON UTF-8 字节。
5. 使用 ECDSA P-256 / SHA-256 对字节签名，结果 Base64 编码。

签名值使用 Web Crypto ECDSA 的 64 字节 `r || s`（IEEE P1363）格式，而不是 ASN.1 DER 编码。

示意清单：

```json
{
  "publisher": {
    "id": "publisher-id",
    "name": "Publisher Name",
    "publicKey": {
      "kty": "EC",
      "crv": "P-256",
      "x": "...",
      "y": "..."
    }
  },
  "signature": {
    "algorithm": "ECDSA-P256-SHA256",
    "value": "..."
  }
}
```

签名结果的含义：

- `未签名`：模块仍可安装，仅没有完整性证明。
- `自签名有效`：文件与作者附带公钥匹配，但首次安装无法仅靠自签名确认现实身份。
- `作者密钥已延续`：升级包签名有效，且公钥与本机已安装版本一致，说明升级来自同一密钥控制者。
- `签名异常`：文件、公钥或签名不匹配，仍可由用户安装，但应谨慎确认来源。

导出备份会加入本机设置并重建清单，因此不会沿用作者原始签名，避免把已改变的内容伪装成原始签名包。

## 来源与审核

`source` 可包含 `registry`、`url`、`repository`。从 GitHub/GitLab 实际导入时，管理器会覆盖并补充 `provider`、`owner`、`repo`、`branch` 与 `commit`，用于后续检查仓库版本是否变化。`review` 可包含 `status`、`reviewer`、`reviewedAt`、`reportUrl`。本地包中的这些字段可能由作者自行填写，因此当前只显示为“声明”，不等同于官方认证。

未来社区仓库应维护独立于模块包的发布者公钥目录、撤销列表和审核报告，并通过仓库签名将 `publisher.id` 绑定到真实账号。管理器核心不应硬编码站点 API、作者私钥或审核密钥。

## 安装与升级

- 安装前只显示一次预检，签名、来源、权限、依赖、冲突和扫描提示都不会禁止写入。
- 用户可拒绝可选权限；必需权限随确认安装授予。当前管理器不认识的权限不会授予。
- 模块以 ID 唯一；依赖以 `ID@精确版本` 唯一，同一依赖可多版本共存。重新安装同一精确依赖版本时自动保存旧修订，最多保留 3 个历史版本。
- 依赖缺失、停用、版本不符、传递依赖失败、循环依赖、冲突或平台版本不兼容时，模块可以保持安装，但宿主暂不执行它。
- `conflicts` 对模块和依赖都生效，任意一方声明匹配范围即可阻止双方相关运行链路；这属于兼容性保护，不改变用户能否安装文件。
- Git 仓库导入与更新只接受公开 HTTPS GitHub/GitLab 仓库，下载默认分支 ZIP 后进入与本地包相同的大小、路径、清单、签名和静态风险预检。
- `dependencySources` 只能对应已经声明的依赖，且只能指向公开 GitHub/GitLab HTTPS 仓库。自动下载只负责加入安装审核队列，不会绕过用户确认。
- `exports` 验证依赖创建后的接口形状；`claims` 和静态扫描只提示可能同时占用的全局对象、页面选择器与路由。静态重叠不能证明真实冲突，因此不会自动拒绝安装或擅自停用。
- 签名密钥变化会显示明显提示，但仍保留用户最终决定权。

## 审核建议

社区审核至少应覆盖权限用途、动态代码、远程脚本、Cookie/Token、未过滤 HTML、无限循环、高频定时器、网络目标、事件清理、依赖来源和许可证。审核结论应关联模块 ID、精确版本、包摘要、审核者与时间，版本内容变化后需要重新审核。
